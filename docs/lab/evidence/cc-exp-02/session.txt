  Decisões técnicas não determinadas pelos critérios de aceite nem pelo Spine

  1. Ordem de prioridade quando há mais de um erro: entrada inválida (400),
     depois mesma conta, origem inexistente, destino inexistente e saldo
     insuficiente (todos 422). A story e o Spine não definem essa ordem.
  2. Mesma conta antes de existência: a verificação de mesma conta roda antes de
     consultar o banco. Por isso, a mesma conta inexistente como origem e
     destino responde SAME_ACCOUNT, e não SOURCE_ACCOUNT_NOT_FOUND.
  3. Existência verificada depois dos dois bloqueios: a origem é verificada
     antes do destino, para que a resposta não dependa da ordem dos UUIDs.
     Antes, lockById falhava na primeira conta bloqueada. Removi lockById e
     passei a usar Optional com os dois bloqueios feitos antes de qualquer
     verificação. Com isso, quando uma conta não existe, a outra ainda é
     bloqueada: há um SELECT … FOR UPDATE a mais nesse caso de erro.
  4. Lugar de cada regra:
     - saldo e existência ficam em AccountService, do pacote account;
     - mesma conta fica em TransferService, como regra da transferência;
     - amount > 0 é validado no DTO com @DecimalMin(value = "0.00", inclusive = 
       false).
  5. Hierarquia de exceções: Source… e DestinationAccountNotFoundException

  package dev.agenticlab.account.service;

  import dev.agenticlab.account.model.Account;
  import dev.agenticlab.account.repository.AccountRepository;
  import java.math.BigDecimal;
  import java.util.Optional;
  import java.util.UUID;
  import org.springframework.stereotype.Service;
  import org.springframework.transaction.annotation.Transactional;

  /**
   * Serviço público de {@code account} (AD-2). Nenhum outro pacote acessa
   * {@link AccountRepository} ou {@link Account} diretamente para alterar 
  saldo.
   */
  @Service
  public class AccountService {

      private final AccountRepository accountRepository;

      public AccountService(AccountRepository accountRepository) {
          this.accountRepository = accountRepository;
      }

      @Transactional
      public Account create(BigDecimal initialBalance) {
          Account account = new Account(UUID.randomUUID(), initialBalance);
          return accountRepository.save(account);
      }

      @Transactional(readOnly = true)
      public Account findById(UUID id) {
          return accountRepository.findById(id).orElseThrow(() -> new
  AccountNotFoundException(id));
      }

      /**
       * Debita {@code sourceAccountId} e credita {@code destinationAccountId} 
  pelo mesmo valor,
       * dentro da transação do chamador (AD-3). AD-4: as duas contas são 
  bloqueadas em ordem
       * crescente de id, para evitar deadlock em transferências cruzadas, e o 
  saldo é verificado
       * depois do bloqueio.
       *
       * <p>A existência das contas é verificada depois dos dois bloqueios, 
  origem antes de destino,
       * para que a resposta não dependa da ordem dos ids.
       *
       * @throws SourceAccountNotFoundException se a origem não existe
       * @throws DestinationAccountNotFoundException se o destino não existe
       * @throws InsufficientFundsException se o saldo da origem é menor que 
  {@code amount}
       */
      @Transactional
      public void transferBalance(UUID sourceAccountId, UUID
  destinationAccountId, BigDecimal amount) {
          boolean sourceFirst = sourceAccountId.compareTo(destinationAccountId)
  <= 0;
          UUID firstLockId = sourceFirst ? sourceAccountId :
  destinationAccountId;
          UUID secondLockId = sourceFirst ? destinationAccountId :
  sourceAccountId;

          Optional<Account> first =
  accountRepository.findByIdForUpdate(firstLockId);
          Optional<Account> second =
  accountRepository.findByIdForUpdate(secondLockId);

          Account source =
                  (sourceFirst ? first : second)
                          .orElseThrow(() -> new
  SourceAccountNotFoundException(sourceAccountId));
          Account destination =
                  (sourceFirst ? second : first)
                          .orElseThrow(() -> new
  DestinationAccountNotFoundException(destinationAccountId));

          if (source.getBalance().compareTo(amount) < 0) {
              throw new InsufficientFundsException(sourceAccountId);
          }

          source.debit(amount);
          destination.credit(amount);
      }
  }

  AccountService.transferBalance em detalhe

  Como os dois UUIDs são ordenados

  - A ordem vem de sourceAccountId.compareTo(destinationAccountId) <= 0. Se o
    resultado for verdadeiro, a origem é bloqueada primeiro; se for falso, o
    destino.
  - Essa comparação já existia na versão do CC-EXP-01. Eu mantive o mesmo
    critério.

  Ponto importante para a revisão: java.util.UUID.compareTo compara os 64 bits
  altos e depois os 64 bits baixos como long com sinal. Por isso, essa ordem não
  coincide com a ordem de uuid no PostgreSQL, que compara byte a byte, sem
  sinal.

  - Exemplo: um UUID que começa com 8–f é "menor" em Java do que um que começa
    com 0–7. No banco, é o contrário.
  - Deadlock: como todo o código usa o mesmo comparador, a ordem de bloqueio é
    consistente entre transações. Isso é o que evita deadlock entre
    transferências cruzadas.
  - AD-4: mesmo assim, essa ordem não é a "ordem crescente de id" do banco no
    sentido literal.

  Isso também afeta um dos meus testes.
  unknownDestinationIsReportedWhateverItsLockPosition usa new UUID(0L, 1L) e new
  UUID(-1L, -1L) supondo que eles caiam em lados opostos de um UUID aleatório.
  Pela comparação com sinal, isso não é garantido: dependendo do UUID gerado
  para a origem, os dois casos podem cair do mesmo lado. O teste passa, mas não
  garante que cobre as duas posições de bloqueio. Os UUIDs do teste
  unknownSourceIsReportedFirst… ((0,1) e (MAX,MAX)) ficam em ordem correta.

  Quantos SELECT … FOR UPDATE são executados

  Sempre dois, em todos os caminhos. As duas chamadas a findByIdForUpdate (uma
  consulta JPQL com PESSIMISTIC_WRITE) acontecem antes de qualquer verificação.

  - Consultas JPQL sempre vão ao banco, mesmo que a entidade já esteja no
    contexto de persistência.
  - O caso origem = destino não chega a este método pela API, porque
    TransferService rejeita antes. Se este método fosse chamado direto com o
    mesmo id, também haveria dois SELECTs.

  Só a origem não existe

  1. Os dois SELECT … FOR UPDATE rodam. A linha do destino fica bloqueada; o
     SELECT da origem não retorna linha e não bloqueia nada.
  2. (sourceFirst ? first : second) está vazio, então é lançada
     SourceAccountNotFoundException.
  3. A exceção é uma RuntimeException e atravessa os métodos @Transactional. A
     transação é desfeita e o bloqueio do destino é liberado. Nenhum saldo é
     tocado e nenhuma Transfer é criada.
  4. O handler responde 422 com SOURCE_ACCOUNT_NOT_FOUND.

  Só o destino não existe

  1. Os dois SELECTs rodam. A linha da origem fica bloqueada; o destino não
     bloqueia nada.
  2. A origem é encontrada.
  3. (sourceFirst ? second : first) está vazio, então é lançada
     DestinationAccountNotFoundException.
  4. A transação é desfeita e o bloqueio é liberado. O saldo nem chega a ser
     verificado. O handler responde 422 com DESTINATION_ACCOUNT_NOT_FOUND.

  As duas contas não existem

  1. Os dois SELECTs rodam e nenhum bloqueia linha.
  2. A origem é verificada primeiro, então é lançada
     SourceAccountNotFoundException, seja qual for a ordem dos ids.
  3. O handler responde 422 com SOURCE_ACCOUNT_NOT_FOUND.

  Por que bloquear a conta existente antes de concluir que a outra não existe

  A razão foi o determinismo do código de erro.

  - Se eu parasse no primeiro bloqueio que falhasse, como fazia o lockById
    anterior: com as duas contas inexistentes, o código retornado dependeria de
    qual UUID é menor. Às vezes seria SOURCE…, às vezes DESTINATION….
  - Para sempre dar prioridade à origem, preciso saber se a origem existe mesmo
    quando ela é a segunda da ordem. Isso exige executar a segunda consulta.
  - Escolhi executar essa segunda consulta pelo mesmo caminho com bloqueio, em
    vez de criar uma consulta sem bloqueio. Assim fica um fluxo único que sempre
    bloqueia em ordem fixa (AD-4) e depois verifica.
  - O custo: nos casos de erro, a conta existente fica bloqueada até o rollback,
    o que é um intervalo curto. Também há um SELECT … FOR UPDATE que não seria
    necessário para rejeitar a solicitação.

  Não pesei a alternativa de verificar a existência antes de bloquear. Escolhi o
  caminho único por simplicidade e para respeitar a ordem do AD-4.

  Por que as duas posições agora são garantidas

  - Como o Java compara: UUID.compareTo compara primeiro os 64 bits altos, como
    long com sinal. Os bits baixos só contam em caso de empate.
  - Os extremos: Long.MIN_VALUE é o menor long possível e Long.MAX_VALUE o
    maior. Um destino com esses bits altos fica antes ou depois de qualquer
    origem, a menos que os bits altos empatem.
  - Por que não há empate: a origem vem de UUID.randomUUID(), que é um UUID v4.
    Nele, o nibble de versão nos bits altos vale sempre 4. Em Long.MIN_VALUE
    (0x8000…0000) esse nibble vale 0, e em Long.MAX_VALUE (0x7FFF…FFFF) vale F.
    Então os bits altos nunca empatam com os da origem.
  - Resultado: o primeiro cenário sempre tem o destino como primeiro bloqueio, e
    o segundo sempre tem o destino como segundo bloqueio.
  - Proteção explícita: as duas asserções novas deixam isso verificável. Se a
    premissa falhar algum dia, o teste falha nesse ponto, e não passa sem cobrir
    o que pretende.
